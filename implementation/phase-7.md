### P7-01: Ad Events Migration

**Description:**
Create the `ad_events` table to support the Free plan monetization strategy. Ad events track display and rewarded ad interactions for billing, compliance, and reward eligibility. This table is the audit trail for all ad interactions — every impression, click, and completion is recorded with workspace and user scoping. The table enforces that reward-grant tracking is only possible for completed rewarded ads, aligning with Doc 10's requirement that rewarded ad grants must be server-side verified.

**Technical Details:**

**Table: `ad_events`**

| Column | Type | Constraints | Purpose |
|---|---|---|---|
| id | UUID | PK DEFAULT gen_random_uuid() | Primary key |
| workspace_id | UUID | NOT NULL FK → workspaces(id) | Tenant scoping |
| user_id | UUID | NOT NULL FK → users(id) | User who viewed/interacted |
| ad_type | VARCHAR(20) | NOT NULL CHECK (ad_type IN ('display','rewarded')) | Type of ad interaction |
| placement | VARCHAR(50) | NOT NULL | Where the ad appeared (allowlist enforced at app layer) |
| provider_event_id | VARCHAR(255) | UNIQUE WHERE provider_event_id IS NOT NULL | Dedup by ad provider event ID |
| impression | BOOLEAN | NOT NULL DEFAULT false | Whether the ad was displayed |
| click | BOOLEAN | NOT NULL DEFAULT false | Whether the ad was clicked |
| completed | BOOLEAN | NOT NULL DEFAULT false | Whether the ad was watched to completion (rewarded only) |
| reward_granted | BOOLEAN | NOT NULL DEFAULT false | Whether a reward was issued for this event |
| reward_type | VARCHAR(50) | Nullable | Type of reward (e.g., 'transaction_pool', 'ai_credits') |
| reward_amount | INTEGER | Nullable | Quantity granted |
| created_at | TIMESTAMPTZ | NOT NULL DEFAULT now() | When the event occurred |

**Indexes:**

| Index | Columns | Rationale |
|---|---|---|
| idx_ad_events_workspace_created | (workspace_id, created_at DESC) | Fast queries for workspace ad history and daily cap checks |
| idx_ad_events_user_type_created | (user_id, ad_type, created_at DESC) | Per-user daily/monthly impression and rewarded cap queries |

**Constraint:**
- `reward_granted` may only be `true` when `ad_type = 'rewarded'` AND `completed = true`

**Placement Allowlist (Application Layer):**
- `dashboard_lower`, `dashboard_side_rail`, `transaction_list_after_rows`, `reports_lower`, `settings_upgrade_area`

**Forbidden Placements (Doc 10):**
- Transaction save flows, AI confirmation forms, invoice send/download, wallet payment flows, loan repayment flows, void/correction flows, payment confirmation screens

**Acceptance Criteria:**
- [ ] Migration creates `ad_events` table with all columns and correct types
- [ ] `provider_event_id` unique constraint allows NULL but deduplicates when present
- [ ] Check constraint on `reward_granted` prevents rewards for non-rewarded or incomplete ads
- [ ] Indexes support daily impression cap queries and workspace-scoped lookups
- [ ] Migration is idempotent and runs in CI/CD without manual intervention

### P7-05: Paystack Subscription Webhook Handler

**Description:**
Implement the `POST /api/v1/webhooks/payment-provider` endpoint to receive and process Paystack subscription events. This is the primary mechanism by which the backend learns about subscription state changes — Paystack calls this endpoint when subscriptions are created, charged, disabled, or when payments fail. The endpoint must verify the HMAC-SHA512 signature before processing any event, and must be idempotent so that re-delivered events do not cause duplicate subscription updates. Per Doc 06: must verify webhook signatures before processing; invalid signatures must be rejected; processing must be idempotent. Per Doc 10: webhooks must update subscription state idempotently.

**Technical Details:**

**Endpoint:**

| Method | Path | Auth | Description |
|---|---|---|---|
| POST | /api/v1/webhooks/payment-provider | None (Paystack calls directly) | Receive and process Paystack webhook events |

**Signature Verification:**
1. Read raw request body bytes
2. Compute HMAC-SHA512 of raw body using `PAYSTACK_WEBHOOK_SECRET` environment variable
3. Compare computed hash to `x-paystack-signature` header using `crypto/subtle.ConstantTimeCompare`
4. If mismatch: return `401`, log the attempt (without sensitive data), do NOT store in `webhook_events`

**Request Payload (Paystack format):**
```json
{
  "event": "subscription.create",
  "data": {
    "id": 123456,
    "plan_code": "PLN_xxx",
    "customer": {
      "email": "user@example.com",
      "customer_code": "CUS_xxx"
    },
    "subscription_code": "SUB_xxx",
    "status": "active",
    "paid_at": "2026-06-15T10:00:00Z",
    "next_payment_date": "2026-07-15T00:00:00Z",
    "amount": 600000
  }
}
```

**Processing Steps:**
1. Verify HMAC-SHA512 signature; reject with `401` if invalid
2. Check `webhook_events` for existing `(provider='paystack', provider_event_id=data.id)` — if found, return `200 { "status": "duplicate" }` without re-processing
3. Store incoming event in `webhook_events` with `signature_valid = true`
4. Route to `ApplySubscriptionEvent()` based on `event` type
5. Return appropriate response

**Handled Event Types:**

| Event Type | Action |
|---|---|
| `subscription.create` | Insert/update `subscriptions` row, set workspace plan |
| `subscription.disable` | Set `subscriptions.status = 'cancelled'`, downgrade workspace to Free plan |
| `subscription.enable` | Set `subscriptions.status = 'active'`, restore workspace plan |
| `charge.success` | Update `subscriptions.paid_through_date`, extend plan access |
| `invoice.payment_failed` | Set `subscriptions.status = 'past_due'`, emit notification |

**Response Envelope:**
```json
// Success
{ "status": "processed" }

// Duplicate
{ "status": "duplicate" }

// Invalid signature
// HTTP 401, no JSON body
```

**Security Considerations (Ref: Doc 09):**
- No auth middleware — Paystack calls this directly
- Signature verification is the authentication mechanism
- Payloads must be sanitized before storage (no full card numbers, bank details, or raw PII)
- Constant-time comparison prevents timing attacks on signature verification
- Rate limiting applied at infrastructure level to prevent webhook flooding

**Acceptance Criteria:**
- [ ] Invalid HMAC-SHA512 signatures return `401` and event is NOT stored
- [ ] Valid signatures store event in `webhook_events` with `signature_valid = true`
- [ ] Duplicate `(provider, provider_event_id)` returns `200 { "status": "duplicate" }` without re-processing
- [ ] All 5 event types are handled with correct subscription/plan state updates
- [ ] Processing is atomic — subscription and workspace plan updated in same transaction
- [ ] Webhook payloads are sanitized (no full card numbers or bank details stored)

### P7-06: Plan State Update Logic from Webhooks

**Description:**
Implement the internal service function `ApplySubscriptionEvent()` that atomically updates subscription state, workspace plan, usage counters, and audit trail after a webhook event is validated. This function is called by the webhook handler and must execute all state changes within a single database transaction to prevent partial updates where a subscription is active but the workspace still shows the wrong plan. Per Doc 10: Paystack is the first subscription provider; backend enforces plan limits; webhooks must update subscription state idempotently.

**Technical Details:**

**Function Signature:**
```go
func ApplySubscriptionEvent(ctx context.Context, event WebhookEvent) error
```

**Processing Steps (all within one database transaction):**
1. Upsert `subscriptions` row with: `workspace_id`, `plan_id`, `provider = 'paystack'`, `provider_subscription_code`, `status`, `current_period_start`, `current_period_end`, `paid_through_date`, `cancelled_at`, `updated_at`
2. Update `workspaces.plan_id` to the resolved plan ID
3. On `subscription.create` or `subscription.enable`: reset `usage_counters` for the new billing period (set `current_count = 0`, set `period_start` and `period_end` to new billing cycle)
4. Log the plan change in audit trail with `event_type`, `user_id`, `workspace_id`, old plan, new plan, timestamp

**Plan Resolution Map:**

| Paystack plan_code | Internal Plan | Price |
|---|---|---|
| `starter_monthly` | Starter | NGN 2,500/mo |
| `business_monthly` | Business | NGN 6,000/mo |
| `pro_monthly` | Pro | NGN 12,000/mo |
| (no active subscription) | Free | NGN 0 |

**Downgrade Handling:**
- When subscription is disabled, set `workspaces.plan_id` to Free plan ID
- Existing records remain immutable — only new writes are subject to Free limits
- No data deletion on downgrade
- `usage_counters.current_count` is NOT reset on downgrade — existing usage counts persist but now measured against Free limits

**Security Considerations (Ref: Doc 09):**
- Workspace plan resolution is server-side only — clients cannot supply `plan_id`
- All changes are auditable
- Transaction ensures consistency — if any step fails, entire operation rolls back

**Acceptance Criteria:**
- [ ] `ApplySubscriptionEvent()` executes all state changes in a single database transaction
- [ ] Subscription upsert correctly maps Paystack plan codes to internal plan IDs
- [ ] Workspace plan is updated atomically with subscription state
- [ ] Usage counters reset on new subscription period (create/enable events)
- [ ] Downgrade to Free preserves existing data and usage counts
- [ ] Plan change is logged in audit trail with before/after values
- [ ] Failed transaction rolls back all changes with no partial state

### P7-07: Usage Counter Enforcement

**Description:**
Implement the `EnforcePlanLimit()` service function that checks plan limits before every write operation. This is the central enforcement mechanism for the entire monetization system — it is called before transactions, invoices, loans, wallet deposits, AI calls, exports, and sync operations. If a user's current usage (including bonus from rewarded ads) meets or exceeds their plan's feature limit, the function returns a `PLAN_LIMIT_REACHED` error. On successful writes, the counter is atomically incremented within the same transaction. Per Doc 06: backend enforces plan limits before writes, AI calls, exports, and sync. Per Doc 10: reward grants expand monthly pools only.

**Technical Details:**

**Function Signature:**
```go
func EnforcePlanLimit(ctx context.Context, workspaceID uuid.UUID, feature string) error
```

**Usage Counter Fields:**

| Field | Type | Purpose |
|---|---|---|
| workspace_id | UUID | Tenant scoping |
| feature | VARCHAR(50) | Feature name: 'transactions', 'invoices', 'ai_credits', 'exports', 'wallet_deposits', 'loans' |
| period_start | DATE | Start of current billing period |
| period_end | DATE | End of current billing period |
| current_count | INTEGER | Number of units consumed this period |
| bonus_count | INTEGER | Additional units from rewarded ad grants |

**Effective Limit Calculation:**
```
effective_limit = feature_limits.max_value + usage_counters.bonus_count
```
- `feature_limits.max_value = -1` means unlimited/fair-use (skip enforcement)
- Bonus from rewarded ad grants is added to the base limit, not the current count

**Processing Steps:**
1. Resolve current plan from `workspaces.plan_id`
2. Read `usage_counters` for the given `workspace_id`, `feature`, and current billing period
3. Read `feature_limits.max_value` for the given `plan_id` and `feature`
4. If `max_value = -1`: allow (unlimited/fair-use)
5. If `current_count >= max_value + bonus_count`: return `PLAN_LIMIT_REACHED` error
6. On success: within the same transaction, atomically increment `usage_counters.current_count`

**Error Response:**
```json
{
  "error": {
    "code": "PLAN_LIMIT_REACHED",
    "message": "You have reached your monthly limit for transactions (100/100). Upgrade your plan or watch an ad to unlock more.",
    "details": {
      "feature": "transactions",
      "current_usage": 100,
      "limit": 100,
      "bonus": 0,
      "plan": "free"
    }
  }
}
```

**Rewarded Ad Grant Integration:**
- When a `rewarded_ad_grant` is created, `usage_counters.bonus_count` for the matching `feature` and `pool_month` is atomically incremented
- The bonus is automatically included in the next `EnforcePlanLimit()` check
- Grants only expand monthly pools — they do not unlock per-action gates (Doc 10)

**Acceptance Criteria:**
- [ ] `EnforcePlanLimit()` is called before every write operation (transactions, invoices, loans, wallets, AI, exports, sync)
- [ ] Effective limit includes base plan limit + bonus from rewarded ad grants
- [ ] `PLAN_LIMIT_REACHED` error includes feature name, current usage, limit, bonus, and plan name
- [ ] `current_count` is atomically incremented on successful write within the same transaction
- [ ] Unlimited features (`max_value = -1`) bypass enforcement
- [ ] Counter correctly resets at start of new billing period

2. **P7-05–P7-07 (Webhook handler, plan state, usage enforcement)** are backend-only and must be complete before any plan-gated frontend work can be tested.
3. **P7-08–P7-09 (Plan and usage endpoints)** are needed by almost every frontend component in this phase.
4. **P7-10–P7-11 (Ad event and reward grant backend)** must be ready before frontend AdSlot and RewardedAdPrompt can function.
5. **P7-12 (Sync mutations endpoint)** must be ready before offline queue and sync UI can be tested.
6. **P7-13–P7-14 (PWA shell and service worker)** are foundational and should be set up early but don't block backend work.
7. **P7-15 (IndexedDB offline queue)** depends on P7-12 and P7-13–P7-14.
8. **P7-16–P7-17 (Offline states)** depend on P7-15 and the plan/usage endpoints.
9. **P7-18–P7-19 (Paystack checkout and subscription UI)** depend on P7-05–P7-06 and P7-08.
10. **P7-20–P7-21 (AdSlot and RewardedAdPrompt)** depend on P7-10–P7-11 and plan detection.
11. **P7-22 (Invoice branding)** depends on plan detection and PDF generation logic from Phase 4.
12. **P7-23 (PlanGate)** can be built in parallel with other frontend work but needs P7-08 for plan data.
13. **P7-24 (OfflineBanner)** depends on P7-15 and network detection.

## Key Rules (Cross-Referenced from Planning Docs)

- **Monetization must never block critical financial actions with forced ads** (Doc 10).
- **Rewarded ads only expand monthly pools — never per-action gates** (Doc 10).
- **Backend is the enforcement truth; frontend PlanGate is UX guidance only** (Doc 10/11).
- **Free users: read-only offline. Paid users: full offline creation and sync** (Doc 10).
- **Server wins for finalized records, balances, wallets, loans, invoices** (Doc 04/05/06/09).
- **Offline queue cap: 100 items max** (Doc 04/09).
- **Rewarded ad caps: 3/day, 20/month, 1 grant per expansion** (Doc 10).
- **Display ad caps: 15 impressions/day, 2 slots/desktop page, 1 slot/mobile screen** (Doc 10).
- **No ads in financial confirmation flows** (Doc 10/11).
- **Webhook signatures must be verified; processing must be idempotent** (Doc 06/09).
- **Idempotency keys required for all offline mutations and reward grants** (Doc 05/06/09).
- **Do not store long-lived auth secrets in IndexedDB or localStorage** (Doc 09).
- **All monetary values as decimal strings at API boundary; NUMERIC(20,4) in PostgreSQL** (Doc 05/06/09).
